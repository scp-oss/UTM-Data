# UTM Дашборд

Веб-приложение на Go для мониторинга нескольких УТМ (Универсальный
транспортный модуль ЕГАИС): хранит список УТМ по IP-адресу, периодически
опрашивает их HTTP API, показывает организацию (ИНН/название), адрес
установки и сроки действия сертификата доступа к ЕГАИС и ГОСТ-сертификата,
и присылает уведомления в Telegram за 30, 10, 5, 2 и 1 день до истечения
любого из сертификатов.

## Возможности

- Форма добавления УТМ — нужен только IP-адрес (и опционально порт, название).
- ИНН, название организации и адрес установки подтягиваются автоматически
  при опросе через официально документированный HTTP API УТМ.
- При добавлении УТМ опрашивается сразу; далее — по расписанию.
- Расписание опроса (1 или 2 раза в сутки, время ЧЧ:ММ) задаётся на
  странице «Настройки», без перезапуска приложения.
- Кнопка ручного опроса каждого УТМ отдельно.
- Telegram-уведомления за 30, 10, 5, 2 и 1 день до истечения сертификата
  ЕГАИС или ГОСТ-сертификата; при продлении сертификата (изменении даты
  окончания) расписание уведомлений сбрасывается автоматически.
- Бот отправляет сообщения напрямую, через SOCKS5-прокси или через
  сторонний relay-сервер, зеркалирующий Bot API — переключается на
  странице «Настройки» без перезапуска, режим проверяется при каждой
  отправке.
- Получателей уведомлений можно привязать к конкретному УТМ (клиенту) —
  тогда они видят только его алерты и не путаются с чужими; получатель
  без привязки получает уведомления по всем УТМ.
- Управление УТМ (добавление/изменение/удаление) и страница настроек
  закрыты паролем администратора; пароль хранится только в переменной
  окружения, не в коде и не в базе данных.
- Работает как обычный Go-бинарник (без контейнера) или в Docker/compose.
- База данных — SQLite (файл), драйвер на чистом Go, без cgo.

## ⚠️ Как УТМ на самом деле отдаёт данные (важно прочитать)

Официальная документация ФСРАР
(`https://fsrar.gov.ru/opendata/dist/documentation.pdf`) **не содержит**
простого JSON/XML-эндпоинта вида `GET /info`. Реальный, документированный
способ получить данные организации — это:

1. `GET /diagnosis` — возвращает XML с полями сертификата доступа к ЕГАИС;
   поле `CN` — это FSRAR_ID вашей УТМ.
2. Документ `QueryClients` (тип `QueryPartner`) с параметром запроса «СИО»,
   равным этому же FSRAR_ID, отправляется как multipart-файл на
   `POST /opt/in/QueryPartner`. УТМ сразу отвечает квитанцией с UUID —
   это **асинхронный** запрос к центральному серверу ЕГАИС, а не локальный
   вызов, и может занять до ~2 минут — опрос УТМ поэтому всегда выполняется
   в фоне, не блокируя браузер.
3. `GET /opt/out?replyId=<uuid>` опрашивается, пока не появится документ
   `ReplyPartner`, затем он забирается (и одновременно удаляется из
   очереди) через `POST` по указанной ссылке.
4. XML `ReplyPartner` содержит ИНН, КПП, название и адрес организации.

Всё это реализовано в `internal/utmclient/client.go` и покрыто тестом
(`client_test.go`) с эмулятором УТМ, воспроизводящим именно эту схему.

**Сроки действия сертификатов (ЕГАИС и ГОСТ) в этом API не документированы
вообще** — по спецификации они отображаются только на домашней странице
самой УТМ (`/app`, SPA), а не как поле ответа. Дашборд дополнительно
пытается вытащить эти даты эвристикой — простым поиском по странице
`/home` (более старой, предположительно серверной, а не SPA) рядом с
известными подписями «Период действия ключа доступа к ЕГАИС» и «Период
действия ГОСТ сертификата» — но это не гарантированный контракт: если
разметка вашей версии УТМ отличается, автоматически ничего не найдётся.

На этот случай сроки действия обоих сертификатов можно **ввести или
поправить вручную** на странице «Изменить УТМ» — посмотрите их на
домашней странице УТМ (раздел «Сертификаты» в настройках) или в самом
файле сертификата. Автоматический опрос никогда не затирает уже известные
значения пустотой: если очередной опрос не смог определить дату сам, ранее
сохранённое (введённое вручную или найденное раньше) значение остаётся.

## ⚠️ УТМ по умолчанию блокирует внешние IP-адреса

По документации, УТМ принимает запросы к своему локальному HTTP API только
с доверенных IP-адресов (по умолчанию — только `127.0.0.1`). Чтобы дашборд
(запущенный на отдельном сервере) вообще смог опрашивать УТМ, на **каждой**
контролируемой УТМ нужно один раз добавить IP-адрес сервера с дашбордом в
доверенные:

- через интерфейс: `http://<ip_утм>:8080/app/settings` → «Фильтр
  IP-адресов» → «Доверенные»;
- либо через `…/UTM/transporter/conf/transport.properties`, параметр
  `web.server.access.ip`.

Без этого шага опрос будет завершаться ошибкой соединения независимо от
корректности кода.

## Диагностика: «ответ ЕГАИС (ReplyPartner) не получен за …»

Эта ошибка означает, что первые два шага прошли (получен FSRAR_ID, УТМ
принял QueryPartner и выдал квитанцию с UUID), но ответ от центрального
сервера ЕГАИС так и не появился в `/opt/out` за отведённое время. Это
происходит на стороне ЕГАИС/УТМ, а не в коде дашборда, и обычно означает
одно из:

- УТМ фактически не подключена к серверу ЕГАИС (нет интернета, сертификат
  недействителен, лицензия не активна) — проверьте статус на домашней
  странице самой УТМ;
- организация ещё не зарегистрирована как отвечающая на такие запросы —
  см. в документации раздел «Сервис «Добавление организации»»;
- сервер ЕГАИС в моменте отвечает медленнее, чем обычно.

Логи контейнера показывают, на каком именно шаге застряло (`docker compose
logs -f utm-dashboard`): получен ли FSRAR_ID, отправлен ли QueryPartner
(с каким UUID) и сколько попыток опроса `/opt/out` было сделано.

Чтобы проверить руками, независимо от дашборда, с машины, у которой есть
доступ к самой УТМ:

```bash
# 1. Получить FSRAR_ID
curl http://<ip_утм>:8080/diagnosis

# 2. Подставить его в CN дважды и отправить запрос (замените 030000199312)
cat > query.xml <<'EOF'
<?xml version="1.0" encoding="UTF-8"?>
<ns:Documents Version="1.0"
xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance" xmlns:ns="http://fsrar.ru/WEGAIS/WB_DOC_SINGLE_01"
xmlns:qp="http://fsrar.ru/WEGAIS/QueryParameters">
<ns:Owner><ns:FSRAR_ID>030000199312</ns:FSRAR_ID></ns:Owner>
<ns:Document><ns:QueryClients><qp:Parameters><qp:Parameter>
  <qp:Name>СИО</qp:Name><qp:Value>030000199312</qp:Value>
</qp:Parameter></qp:Parameters></ns:QueryClients></ns:Document>
</ns:Documents>
EOF
curl -F "xml_file=@query.xml" http://<ip_утм>:8080/opt/in/QueryPartner
# ответ вида <A><url>UUID</url>...</A> — UUID и есть replyId

# 3. Опрашивать, пока не появится ReplyPartner (замените UUID)
curl "http://<ip_утм>:8080/opt/out?replyId=UUID"
```

Если шаг 3 стабильно не отдаёт ссылку на `ReplyPartner` даже спустя
несколько минут ручного ожидания — проблема на стороне УТМ/ЕГАИС, не в
дашборде, и её нужно решать через саму УТМ (её домашнюю страницу и логи)
или поддержку ФСРАР.

## Быстрый старт (Docker Compose)

```bash
git clone <адрес_репозитория> utm-dashboard
cd utm-dashboard
cp .env.example .env
# отредактируйте .env: задайте ADMIN_PASSWORD и, при необходимости,
# нестандартный DASHBOARD_PORT
docker compose up -d --build
```

Дашборд будет доступен на `http://<сервер>:${DASHBOARD_PORT}` (по
умолчанию `8088`). База данных сохраняется в `./data/utm-dashboard.db` на
хосте — том смонтирован, при обновлении контейнера данные не теряются.

### Как обновить

```bash
cd utm-dashboard
git pull
docker compose up -d --build
```

`docker compose up -d --build` пересобирает образ из обновлённого кода и
перезапускает контейнер; смонтированный том с базой данных (`./data`)
сохраняется между обновлениями. `.env` в репозиторий не коммитится
(см. `.gitignore`), поэтому `git pull` никогда не затирает ваши настройки
порта/пароля.

### Нестандартный порт

Порт задаётся в `.env` (переменная `DASHBOARD_PORT`), а не хардкодится в
`docker-compose.yml` — так его не нужно каждый раз указывать вручную при
`docker compose up`:

```bash
echo "DASHBOARD_PORT=9090" >> .env
docker compose up -d --build
```

## Запуск без контейнера

Требуется Go 1.26+.

```bash
go build -o utm-dashboard .
DB_PATH=./data/utm-dashboard.db HTTP_ADDR=:8088 ADMIN_PASSWORD=... ./utm-dashboard
```

Откройте `http://localhost:8088`.

## Конфигурация

Через переменные окружения (только то, что нужно на старте процесса):

| Переменная       | По умолчанию               | Назначение                                                    |
|------------------|------------------------------|----------------------------------------------------------------|
| `HTTP_ADDR`      | `:8088`                     | Адрес веб-интерфейса дашборда (при запуске без Docker)          |
| `DASHBOARD_PORT` | `8088`                       | Порт на хосте при запуске через docker-compose (см. `.env`)     |
| `DB_PATH`        | `./data/utm-dashboard.db`   | Путь к файлу базы данных SQLite                                 |
| `ADMIN_PASSWORD` | *(пусто)*                   | Пароль администратора; без него панель управления открыта всем  |

Всё остальное (токен Telegram-бота, способ доставки/прокси, получатели,
расписание опроса) настраивается в веб-интерфейсе на странице «Настройки»
и хранится в БД — секретов в коде или в репозитории нет.

## Настройка Telegram-бота

1. Создайте бота через [@BotFather](https://t.me/BotFather), получите токен.
2. Вставьте токен на странице «Настройки».
3. Выберите способ доставки:
   - **Напрямую** — обычный запрос к `api.telegram.org`;
   - **Через SOCKS5** — если `api.telegram.org` недоступен напрямую,
     укажите адрес прокси вида `socks5://user:pass@host:1080`;
   - **Через relay-сервер** — сторонний сервис, зеркалирующий Bot API под
     своим доменом с собственным ключом авторизации (например,
     `https://ваш-relay/bot<TOKEN>/sendMessage?auth=<ключ>`); укажите адрес
     relay-сервера и ключ.

   Способ проверяется заново при каждой отправке — переключение не требует
   перезапуска приложения.
4. Узнайте chat_id получателя (например, через
   [@userinfobot](https://t.me/userinfobot) для личных сообщений, либо
   добавив бота в группу — для групповых уведомлений chat_id отрицательный).
5. Добавьте chat_id на странице «Настройки»; при желании привяжите его к
   конкретному УТМ, чтобы этот получатель видел только его уведомления
   (получатель без привязки получает уведомления по всем УТМ). Отправьте
   тестовое сообщение, чтобы проверить доставку.

## Структура проекта

```
main.go                — точка входа, сборка компонентов, graceful shutdown
internal/config         — конфигурация из переменных окружения
internal/models          — доменные типы
internal/db               — открытие SQLite и схема (schema.sql)
internal/store              — доступ к данным (CRUD)
internal/auth                 — вход по паролю администратора (сессии в памяти)
internal/utmclient              — опрос HTTP API УТМ (см. предупреждение выше)
internal/notifier                — отправка сообщений в Telegram (direct/socks5/relay)
internal/scheduler                — расписание опроса и логика уведомлений
internal/web                       — HTTP-обработчики и HTML-шаблоны
documentation.pdf                   — официальная спецификация УТМ от ФСРАР
```
